# Discord 테스트 서버 E2E

기본 모집 인원은 10명입니다. 운영 설정인 `config/config.yaml`에서도
`participant_limit: 10`을 사용합니다. 소수 인원 E2E가 필요할 때만 테스트 중에
일시적으로 값을 낮추고, 테스트 종료 후 반드시 10명으로 되돌립니다.

## 자동 검증과 실제 Discord 검증

GitHub Actions CI는 Python 3.13에서 테스트·컴파일·의존성 검사를 수행합니다.
CI는 main 대상 PR과 수동 실행에서 동작하며 main push에서는 실행하지 않습니다.
main 반영 시 별도 배포 이미지 빌드와 기존 정책 주소의 이동 안내 배포가 실행됩니다.
토큰·운영 DB 없이 실행하는 검사이며 아래 실제 서버 E2E를 대신하지 않습니다.
테스트 길드에서 확인한 커밋·시각·실제 참여 계정 수와 결과를 별도로 기록합니다.

구조 변경 후에도 공개 명령 6개와 반응·티어 listener가 모두 등록되어야 합니다.
구조·시작과 종료 순서·복구 보장 범위는 [코드 아키텍처](architecture.md)를 참고합니다.
모집 공지 전송·활성화·최초 ✅ 추가 도중 실패하면 해당 내전만 취소·정리되고,
다른 내전은 계속 운영되는지 확인합니다.

## 1. 사전점검

개인정보처리방침·지원 안내의 원본은 OWKR Docs에서 관리하며, [공개 준비 목록](legal/README.md)에서 별도로
관리합니다. 현재 공개 전 초안이며 개인정보 삭제 기능의 완료를 의미하지 않습니다.

최소 권한 점검 시 다음도 확인합니다.

- 관련 없는 텍스트·음성 채널 접근이 차단되어 있고, 다른 역할의 상속도 확인
- 전체 멘션·메시지 관리·역할 관리 권한 없이 유저 멘션과 ✅ 반응 추가·복구 동작
- 역할 알림을 사용하면 전용 역할의 멘션 가능 설정과 일반 사용자의 멘션 가능 영향 확인
- 허용하지 않은 역할·사용자와 `@everyone`·`@here`가 봇 메시지에서 알림을 발생시키지 않음
- 티어 수집·수정·복구를 검증하기 전에는 Message Content Intent 비활성화 금지

### 경고와 개인정보 추가 점검

- `channels.warning`에 기존 전용 채널을 설정하고, 미설정·다른 채널·일반 사용자는 `/경고`가 거부되는지 확인
- `/경고 대상:@유저 작업:기록 사유:노쇼`와 비매너를 각각 상의 완료 버튼으로 확정. 확인 전에는 횟수 변화 없음
- 더블 클릭·재시도로 가산되지 않음. 조회·결과는 ephemeral이며 대상 멘션 알림·자동 제재 없음
- 같은 사유 최근 경고 취소, 여러 관리자 동시 취소, 전체삭제 확인과 재시작 후 횟수 확인
- 확인창을 연 뒤 관리자 역할 상실·대상 탈퇴·재가입이면 실행 거부
- 탈퇴한 경고 대상은 정기 조회에서 삭제. 재가입자는 이전 재적 기록 정리. 권한·네트워크 오류와 Unknown Guild는 삭제하지 않음
- `/개인정보`는 일반 사용자도 본인에게만 확인 가능. 타인의 삭제 버튼 실행 불가
- 본인 티어 삭제 후 현재 내전의 답장·수정·재시작 보완 수집으로 원문이 복원되지 않음. 참가·대기와 다른 이용자 정보는 유지
- 시작·취소 내전의 세션·참가·반응·티어·연결·알림이 약 10초 내 정리되고, 다른 활성 내전은 유지
- 중단 중 시작된 내전과 과거 DB의 시작·취소 기록은 재시작 시 정리. 외래 키 무결성과 다른 활성 내전 routing 확인
- 정책 주소·문의 경로 미설정 시 준비 중 안내, 설정 시 HTTPS 링크와 실제 연락처 표시
- 운영 DB·백업의 삭제 검증은 복사한 테스트 자료에서 먼저 수행. 아래 기존 E2E에서 시작·취소 후 DB를 검사할 때는 이제 세션 삭제를 기대

봇을 중지한 상태에서 실행합니다.

```bash
source .venv/bin/activate
python -m src.e2e_preflight
```

또는 설치된 명령을 사용합니다.

```bash
owkr-gather-bot-e2e-check
```

사전점검은 Discord 데이터를 변경하지 않습니다. 다음 항목을 읽기 전용으로 확인합니다.

- 봇 토큰과 테스트 길드 연결
- Message Content Intent
- 명령·모집 공지·티어·관리자·대기실 채널 존재 여부
- 채널별 봇 최소 권한
- 관리자 역할과 모집 알림 역할
- 모집 역할의 실제 멘션 가능 여부
- 필수 슬래시 명령 6개가 테스트 길드에 등록됐는지

`FAIL`이 하나라도 있으면 종료 코드 1을 반환합니다. `WARN`은 테스트 진행은 가능하지만 운영 설정을 다시 확인해야 하는 항목입니다.

코드에서 슬래시 명령 이름을 변경한 직후에는 기존 서버 명령과 달라 실패할 수 있습니다. 이 경우 봇을 한 번 실행해 `guild application commands synced` 로그를 확인한 뒤 사전점검을 다시 실행합니다.

## 2. 봇 실행

파일럿 봇은 한국 시간 월~목 20:00~다음 날 02:00, 금~일 24시간 운영합니다.
VM 운영 시간 타이머를 설치했다면 테스트 중 자동 종료되지 않도록 먼저
`sudo systemctl stop owkr-hours.timer`로 일시 중지하고, 테스트 후 다시 활성화하여
`sudo systemctl start owkr-hours.service`로 현재 시간에 맞춥니다.
월요일 02:00 종료, 목요일 20:00부터 주말 연속 운영, 금요일 낮 유지와
VM 재부팅 후 약 1분 내 시간 조정도 확인합니다. 백업과 시간 조정이 겹쳐도
같은 잠금으로 직렬화되고, 오전 6시 백업이 중지된 봇을 켜지 않아야 합니다.
비운영 시간의 Discord 이벤트·알림은 실시간으로 처리되지 않으며, DB 정리도
다음 가동까지 지연됩니다. 실제 10명 참여 흐름은 운영 시간 안에서 검증합니다.

Docker에서는 [VM 배포 안내](oracle-free-deployment.md)에 따라 빌드한 뒤 실행합니다.
최초 실행으로 명령이 등록된 다음 봇을 중지하고 사전점검을 다시 실행합니다.
테스트 중 `docker compose stop bot`으로 정상 종료하고, 로그에서 종료 오류와
강제 종료(종료 코드 137)가 없는지 확인합니다. `docker compose start bot` 이후
참가·대기·티어 상태와 알림 중복을 확인합니다.
백업·복원은 운영 DB가 아닌 복사본으로 먼저 확인하며 개인정보 삭제 요청도 반영합니다.

```bash
OWKR_LOG_LEVEL=DEBUG python -m src.main
```

로그에서 다음 문구를 확인합니다.

```text
SQLite connected and migrations completed
active session recovery completed
guild application commands unchanged; sync skipped
bot ready
```

명령 구조가 변경된 최초 실행에는 `guild application commands synced`가 표시될 수 있습니다.

## 3. 10명 기준 기본 흐름

1. 관리자 역할이 있는 계정으로 `/내전`을 실행합니다.
2. **시간·모드 수정**을 눌러 기존 값이 채워지는지 확인하고 값을 수정합니다.
3. 갱신된 일정 확인창에서 **생성**을 누릅니다.
4. 생성 결과의 **모집 공지 보기** 링크가 올바른 공지로 이동하는지 확인합니다.
5. 모집 카드에서 시작 시각·✅ 참가 방법, 티어 마감·대기실 입장이 구분되는지 확인합니다. 시각은 한국 시간 기준 `오후 2시`·`오후 2시 30분` 형태에 굵게·밑줄이 적용되고 연월일·상대 시각·코드 배경이 없어야 합니다. 관리자 추가 안내와 주의사항이 누락되지 않고, 모바일에서도 일정 칸이 읽혀야 합니다. 상세 이용 안내 링크는 설정된 경우에만 표시되며 공개 내전 코드가 없어야 합니다.
6. 서로 다른 10개 계정이 ✅을 누릅니다.
7. 모집 완료 공지가 한 번만 전송되고 공개 내전 코드가 없는지 확인합니다.
8. 티어 채널에 내전별 안내 메시지가 생성되는지 확인합니다.
9. 10명 모두 해당 내전 안내 메시지에 `뿅뿅이#31243/챔1/챔1/챔1`처럼 답장으로 티어를 작성합니다. 답장 없는 새 메시지는 저장되지 않는지 별도로 확인합니다.
10. `/티어현황`에서 10명 모두 작성 완료인지 확인합니다.
11. 티어 메시지를 수정한 뒤 최신 원문이 반영되는지 확인합니다.
12. 티어 메시지를 삭제해 미작성 상태로 바뀌는지 확인합니다.
13. 다시 작성한 뒤 작성 완료로 복구되는지 확인합니다.
14. 미작성자 또는 전원 완료 관련 자동 멘션이 전송되지 않는지 확인합니다.
15. `/내전상태`·`/공지문구`가 등록 명령에서 사라졌는지 확인합니다. 모집 완료 전 `/티어현황`도 참가·대기 인원을 보여야 합니다.

## 4. 다중 내전 흐름

1. 같은 시작 시각으로 내전 2개를 만들고, 두 내전과 1시간 이상 차이나는 내전 1개를 생성합니다.
2. `/티어현황`의 내전 선택 자동완성에서 세 내전을 확인하고 각각 참가·대기 인원을 조회합니다.
3. 앞의 두 내전은 대기실1·2로 나뉘고, 같은 시간대의 세 번째 내전은 공지를 만들기 전에 거부되는지 확인합니다.
4. 빈 대기실 없음과 시간 변경 또는 기존 내전 취소 안내가 표시되는지 확인합니다. 생성 확인을 중복 클릭하거나 같은 요청을 재시도해도 한 번만 생성되어야 합니다.
5. 각 모집 공지에 서로 다른 계정으로 반응해 참가자가 섞이지 않는지 확인합니다.
6. 제출 가능한 내전이 하나·여러 개일 때 모두 답장 없는 새 메시지가 저장되지 않는지 확인합니다. 일반 채팅에 오류 답장을 보내지 않아야 합니다.
7. 각 기준 메시지에 답장했을 때 선택한 내전에만 저장되는지 확인합니다.
8. `/내전취소`의 확인 버튼으로 하나만 취소하고 나머지 두 내전이 유지되는지 확인합니다.
9. 취소 성공 후 모집 공지가 모든 반응과 함께 삭제되고 시작 시각을 포함한 취소 안내가 새로 남으며, 본인 전용 결과가 남는지 확인합니다. 공개 안내는 사용자·역할 멘션을 보내지 않으며, 취소 안내에는 ✅ 반응이 없어야 합니다. 공지가 이미 삭제되었거나 삭제·전송 중 권한·네트워크 오류가 있으면 취소 자체는 유지하고 관리자에게 직접 안내할 내용을 알려야 합니다.

## 5. 대기실 배정과 재시작

1. 시작 시각 차이가 59분인 내전 두 개를 순서대로 생성합니다.
2. 먼저 만든 내전은 대기실1, 나중 내전은 대기실2로 표시되는지 확인합니다. 같은 시작 시각도 동일하며, 동시에 3개 생성 요청을 보내도 2개만 성공해야 합니다.
3. 시작 시각 차이가 정확히 1시간이면 기존 방을 다시 예약할 수 있는지 확인합니다. 대기실1 내전을 취소한 뒤 새 내전을 생성하면 대기실1을 재사용하고 기존 대기실2 배정은 유지되어야 합니다.
4. 대기실 안내 직전에 봇을 재시작합니다.
5. 재시작 후에도 각 내전의 배정 대기실이 유지되는지 확인합니다. 모집 카드·모집 완료·대기실 안내의 음성방 멘션을 클릭하면 배정된 방으로 연결되는지 확인합니다. 자동 음성 연결을 강제하지 않으며 Discord 입장 확인창이 표시될 수 있습니다.
6. 배정된 대기실에 들어온 참가자는 제외되고 미입장자만 멘션되는지 확인합니다.
7. 전원이 입장한 상태에서는 공개 대기실 안내가 생성되지 않는지 확인합니다.
8. 티어 안내 메시지를 삭제해 같은 내전의 안내만 다시 생성되는지 확인합니다.
9. 재시작 후 `/티어현황`의 참가·대기·티어 작성 상태와 알림 중복 여부를 확인합니다.

## 6. 테스트 종료

- 테스트용 활성 내전은 `/내전취소`로 각각 정리합니다.
- 테스트 결과에는 시각, 커밋 SHA, 사용한 계정 수와 실패 항목을 기록합니다.
- 테스트에서 모집 인원을 낮췄다면 `participant_limit`을 10으로 되돌립니다.
- 명령 채널과 모집 공지 채널을 분리해서 운영하려면 `channels.announcement`를 공지 전용 채널 ID로 변경합니다.

## 단순화 변경의 호환성 점검

- 과거 DB에 답장 없이 이미 연결된 티어 메시지는 수정·삭제와 재시작 복구를 계속 처리합니다.
- 새 답장은 올바른 내전 안내·서버·채널·참가자·마감 조건을 만족해야 합니다.
- 기존 설정에 `managers.*.pick_limit`, `ban_list`가 남아도 시작이 실패하지 않고, 해당 문구는 공지에서 빠져야 합니다. 기본 모드·추가 안내는 유지합니다.
- 기존 모집 완료 템플릿·티어 안내 YAML은 자동 초기화하지 않습니다. 운영자가 파일을 바꾼 경우 다음 전송을 테스트합니다.
- 대기실 2 자동 배정과 외부 웹 연동 준비용 export·전송 계약은 유지합니다.

## 기본 안내 예시 확인

## 공개 안내 링크 확인

- Pages 배포 후 목차를 포함한 다섯 페이지가 로그인 없이 HTTPS로 열리는지 확인한다.
- 모바일에서 문서를 읽고 이메일 링크를 열 수 있어야 한다.
- 초안 상태에서는 Developer Portal·운영 봇의 최종 정책 URL로 등록하지 않는다.
- 최종 정책 확정 후 `/개인정보`의 처리방침·약관 링크와 웹 문서가 일치하는지 확인한다.

취소의 DB 반영과 Discord 삭제·전송은 원자적이지 않습니다. 처리 중 프로세스가 강제 종료되면
관리자가 남은 모집 공지나 누락된 취소 안내를 수동 정리합니다. 정상 요청의 재시도·중복 클릭은
이미 취소한 세션에 새 취소 안내를 중복 전송하지 않아야 합니다.
