# 삭제 요청·백업 복원 검증

검증일: 2026-10-29

## 범위와 결론

실제 저장소 구현·Discord 삭제 확인 콜백·백업 생성·만료 정리를 가상 데이터와
격리된 임시 폴더에서 연결해 검증했다. Discord API 응답만 모의 객체를 사용했다.
운영 DB·Discord 메시지·메일·요청 대장·VM·Mac의 기존 백업은 읽거나 변경하지 않았다.
Oracle 접속과 운영 복사본 점검은 보류 중이다.

자동 검증은 `tests/test_erasure_recovery.py`의 세 시나리오로 재실행할 수 있다.

```bash
.venv/bin/python -m pytest tests/test_erasure_recovery.py -q
```

| 시나리오 | 확인 결과 |
| --- | --- |
| 본인 티어 삭제 확인 콜백 | 원문·메시지 연결 삭제, 참가·대기 상태와 경고 보존, 비공개 응답 |
| 동일 길드의 두 활성 내전 | 두 내전 모두 해당 사용자 재수집 차단. 다른 참가자와 타 길드 자료 보존 |
| 삭제 후 만든 백업 복원 | 삭제 상태와 수집 중단 유지. SQLite 재연결 후에도 유지 |
| 삭제 전 VM·Mac 백업을 본뜬 두 복사본 복원 | 삭제 전 정보가 남아 있음을 먼저 확인. 요청을 두 번 재반영해도 동일 결과, 재시작 후 삭제·수집 중단 유지 |
| 뒤늦은 저장·새 티어 답장 | 대기 중이던 저장으로 원문이 되살아나지 않음. 새 답장도 수집 중단으로 처리 |
| 백업 원본과 DB 무결성 | 복원용 파일에서만 요청 재반영. 백업 원본 해시 유지, SQLite 무결성·외래키 검사 통과 |
| 두 백업 위치의 7일 만료 | 만료 전 보존, 미리보기는 삭제하지 않음, 만료 후 적용 시 두 복사본 정리. 현행 DB 보존 |

## 완료로 해석하면 안 되는 범위

- `/개인정보`의 티어 삭제 버튼은 기존 백업·로그·경고·Discord 원문을 삭제하지
  않는다. 실제 콜백도 이 한계를 안내하는지 확인했다.
- 삭제 전 백업을 복사해 시작하는 것만으로는 삭제 요청이 반영되지 않는다.
  시작 시 자동 재반영 기능은 없다. 요청 대장에 따라 **복원 후 Discord 연결 전**
  `SafetyService.erase_tiers`에 해당 길드·사용자 요청을 다시 적용해야 한다.
  검증에서는 실제 서비스 메서드로 이 단계를 수행했다. 경고 삭제·탈퇴 정리 요청과
  티어 원문 삭제 요청의 범위를 혼동하지 않는다.
- 티어 수집 중단은 현재 참가 중인 내전 범위다. 향후 새 내전까지 영구 차단하는
  정책으로 확대하지 않았다.
- 보관 중인 백업에 원문이 남을 수 있다. 이 검증은 논리적 삭제·복원 차단·만료
  파일 정리를 확인하며, 디스크·파일시스템 스냅샷의 물리적 복구 불가능성을 증명하지 않는다.
- 가상 VM·Mac 폴더는 실제 서버·Mac의 타이머 실행, 접근 통제, 모든 복사본의
  존재 여부를 검증하지 않는다. 메일 접수·본인 확인·답변 전달도 별도 실제 운영 점검이다.

## 운영에서 남은 점검

1. 실제 삭제 요청의 본인 확인·범위·접수 시각·처리 결과를 접근 제한 대장에 기록한다.
2. 현행 DB와 VM·Mac·추가 수동 복사본 목록을 대조한다. 기존 백업의 보관·삭제
   처리와 로그·Discord 원문 등 별도 처리가 필요한 자료를 구분한다.
3. 봇을 중지한 채 별도 복원 위치에 백업을 복사하고, 백업 이후 요청을 빠짐없이
   재반영한다. 미반영 요청이나 처리 방법이 불명확하면 봇을 시작하지 않는다.
4. 원문·연결 삭제, 해당 내전 재수집 중단, 무관 사용자 보존, DB 무결성을 확인한다.
5. 각 복사본의 파기·만료 정리 실행 결과를 확인하고, 완료·보관 중·미확인 범위를
   구분해 요청자에게 답변한다. 전체 복사본 확인 전에는 전체 삭제 완료로 안내하지 않는다.

이 문서는 검증 기록이며 공개 정책 원본이 아니다. 공개 정책은 OWKR Docs에서 관리한다.
