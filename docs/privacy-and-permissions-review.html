OWKR Gather Bot · 작성·공식 자료 확인: 2026-10-27 KST · 아래 본문은 최초 점검 당시의 기록

후속 구현: 내전 DB 기록은 시작·취소 후 정리하고 경고는 재적 중 보관하도록 결정했다. 관리자 경고 조회·기록·취소·전체삭제, 본인 티어 원문 삭제와 재수집 중단, 정책·문의 안내 설정을 추가했다. 최신 정책과 남은 공개 준비 항목은 문서 관리 안내와 저장소 README를 따른다. 아래 미구현·미확정 표시는 최초 점검 시점의 상태이며 현재 상태와 다를 수 있다. 봇 운영·개인정보 보호 담당은 개발자 겸 내전 총관리자 qtaghdi, 기본 문의는 qtaghdi@gmail.com, 보조 문의는 Discord qtaghdi의 DM으로 정했다. 법정 책임자 표시 요건 확인·공개 주소·로그/백업 절차·실제 Discord 검증은 여전히 필요하다.
결론: 기능에 필요한 권한은 이미 좁은 편이다. 우선 관련 채널에만 접근하도록 제한하고, 개인정보 보관·삭제를 마련한다. 가장 큰 권한 축소 후보는 Message Content이지만, 답장·수정·재시작 복구를 검증하기 전에는 끄지 않는다.

이 문서는 공개 개인정보처리방침이나 심사 통과 보증이 아니다. 저장소의 코드와 문서를 조사한 결과이며 실제 Developer Portal, Discord 역할·채널 설정, 운영 VM·백업 저장소는 확인하지 않았다. 제안은 구현·배포된 동작과 구분한다.

지정 티어 채널에서 참가자·시간 조건에 맞는 메시지를 저장한다. 다만 수신 가능한 데이터와 실제 영구 저장하는 데이터는 다르며, 코드의 채널 필터만으로 Discord 접근 권한 자체가 줄어드는 것은 아니다. 현재 재시작 보완 수집은 티어 채널의 과거 이력을 전체 순회한 뒤 활동 시각을 판별한다.

확인된 공백: 종료·취소 내전의 보관 기한과 자동 파기, 개인정보 수정·삭제 요청 경로가 없다. 내전 시작 후 티어 삭제 이벤트는 처리하지 않으며, 시작 전 원문 삭제도 연결 기록·참가 기록·백업까지 지우는 절차는 아니다.

3. 기능을 유지하면서 줄일 수 있는 권한

봇 역할의 서버 전체 권한, 채널별 허용·거부, 다른 역할과 @everyone 상속을 함께 확인한다. 초대 링크의 권한 숫자만 줄여서는 실제 접근이 제한되지 않는다. 서버 전체 권한은 최소화하고 지정 채널에서만 필요한 권한을 허용하는 구성을 권장한다.

대상현재 코드 기준권장 범위·축소 가능성

OAuth2 scope는 현재 bot, applications.commands로 유지하고 사용자 계정용 scope를 추가하지 않는다. 봇 운영 명령 실행 자격과 봇 자신의 권한은 별개다. 기존 관리자 ID/역할 검사와 서버 연동 설정의 명령어 제한을 함께 유지한다.

Message Content 없이 답장 제출이 가능한가?

공식 문서는 일반 봇 메시지에 Discord 답장 기능으로 답장하면서 답장 멘션이 켜져 있는 경우 내용 접근 예외를 인정한다. 슬래시 명령 응답에 대한 답장은 이 예외에 포함하지 않는다. 현재 티어 안내는 일반 봇 메시지로 전송되지만, 멘션을 끈 답장·후속 수정·REST 이력 조회까지 지금과 동일하게 동작한다고 단정할 수 없다.

  1. 우선 실험: 테스트 봇에서 코드와 Portal 양쪽의 Message Content를 끄고 일반 티어 안내 답장의 생성·수정·재시작 복구를 검증한다. 답장 멘션 켬/끔을 각각 확인한다.
  2. 정책과 비교: 멘션 켬을 필수로 해야 한다면 기존의 단순한 “안내에 답장” 흐름에 새 조건이 생긴다. 자동 저장되지 않을 때 안내할 방법도 필요하다. 비답장 제출 호환 동작을 없애는 결정도 별도로 기록한다.
  3. 실험 실패 시 대안: 티어 안내의 “티어 작성” 버튼 → 입력창은 광범위한 메시지 내용 접근을 줄일 수 있다. 다만 공식 답장 제출 정책과 수정·삭제·메시지 연결 방식의 변경이므로 별도 제품 결정 후 구현한다. 사용자에게 두 경로를 동시에 권장하지 않는다.

2026-06-11 공식 안내상 특권 Intent 심사 기준은 설치 서버 전체에서 봇에 접근 가능한 고유 사용자 10,000명이며, 실제 명령 이용자나 내전 참가자 수와 다르다. 통지 후 신청 기간은 90일이고 승인 앱은 매년 재심사 대상이다. 앱 인증과 Intent 심사는 분리되어 있다. 이 기준 미만이어도 개인정보 의무는 유지된다.

5. 검증과 권장 진행 순서

  1. 실제 Discord 권한·Portal·호스팅·백업 현황을 확인하고 운영자와 문의처를 정한다.
  2. 관련 채널만 허용하고 광범위한 관리·멘션 권한을 제거하는 설정안을 테스트 서버에서 검증한다.
  3. 보관·삭제·복원 정책과 안전한 삭제 처리를 먼저 구현한 뒤 실제 동작에 맞는 처리방침을 공개한다.
  4. Message Content 없는 답장 흐름을 실험하고, 정책 변경 여부를 결정한다. 실패하면 기존 설정으로 복구한다.
권한 축소 실험의 통과 조건
  • 모집·대타 공지, Embed, 첫 ✅, 마지막 참가자 이탈 후 ✅ 복구, 자기 메시지 취소 삭제
  • 티어 답장 멘션 켬/끔, 수정·빈 문자열·삭제·일괄 삭제, 비참가자·봇·다른 채널 메시지
  • 오프라인 중 제출·수정·삭제, 재시작 후 연결·명단 복구, 오래된 메시지의 기간 내 수정
  • 중복 이벤트·재시도·동시 반응 순서, 마감·시작 시각 경계, 취소된 내전과 다른 활성 내전의 분리
  • 미입장 대상만 안내, 음성 채널 접근 실패 시 무차별 멘션 없이 재시도, 미허용 역할·사용자 멘션 차단
  • 관리자 ephemeral 응답·공지 미리보기·오류 안내, 채널별 실효 권한과 사전 점검 결과 일치
개인정보 삭제 구현의 통과 조건
  • 진행 중·시작 후·취소 후 요청, 반복 요청, 삭제 처리 중 이벤트 도착과 중단·재시작
  • 원문뿐 아니라 사용자 연결·참가·반응·알림 payload·로그·백업의 처리 범위 확인
  • 타 사용자와 다른 내전의 기록 보존, 삭제 후 대기자 자동 승격 없음
  • 백업 복구와 보완 수집 이후 삭제한 데이터가 재등장하지 않음

구현 변경 시 python -m pytest, python -m compileall src, python -m pip check를 실행한다. 흐름·운영 정책 변경 시 README와 Discord E2E 문서도 함께 갱신한다. 이 검토 기록 자체는 봇 코드나 실제 권한·정책을 변경하지 않는다.
