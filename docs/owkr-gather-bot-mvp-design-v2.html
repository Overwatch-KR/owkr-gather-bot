v2 · 2026-07-16 · Asia/Seoul · 구현 전 검토안

2. 확정한 MVP 규칙

모집

  • 정원 기본값은 10명이며 모드 문자열과 독립
  • 길드당 활성 내전은 1개
  • 첫 정원 도달 시 완료 공지는 한 번만 생성
  • 완료 후 인원이 다시 부족해져도 완료 공지를 재전송하지 않음
  • 시작 전 확정자 제거 시 가장 빠른 대기자 자동 승격

티어와 시간

  • 티어 수집 창의 시작은 완료 공지가 실제 전송된 시각
  • 수집 창 종료는 티어 마감 시각 미만
  • 마감 이후 수정은 저장된 원문을 바꾸지 않음
  • 대기실 안내는 시작 10분 전이지만 로스터를 잠그지 않음
  • 시작 시각부터 roster snapshot을 동결
완료가 너무 늦은 경우: 모집 완료 공지가 티어 마감 이후에 전송되면 유효한 티어 수집 창이 없습니다. 이 경우 자동으로 마감을 연장하지 않고 관리자에게 안내합니다. 마감 연장은 후속 운영 명령으로 별도 설계합니다.

  • 세션별 asyncio.Queue와 actor 1개
  • aiosqlite, WAL, 단일 batch writer

유지할 확장 경계

class MatchRepository(Protocol):
    async def create_match(...): ...
    async def get_active_match(...): ...
    async def apply_reaction_batch(...): ...
    async def upsert_tier_submission(...): ...

class SyncSink(Protocol):
    async def publish(snapshot): ...

# MVP wiring
SQLiteMatchRepository + NoOpSyncSink

FastAPI client, Postgres repository, 원격 sync outbox는 인터페이스만 보존하고 구현하지 않습니다.

단순한 외부 효과 처리

  • raw reaction handler에서는 메모리 routing과 queue 삽입만 수행합니다.
  • actor가 만든 변경을 writer가 1초 또는 100건 단위로 SQLite에 저장합니다.
  • 모집 완료·대기실·관리자 안내는 작은 notification_outbox로 전송합니다.
  • outbox는 PENDING/SENT/FAILED, 시도 횟수, 마지막 오류만 둡니다. dead-letter UI나 재처리 파이프라인은 만들지 않습니다.

4. 상태와 생명주기

CREATED → RECRUITING ⇄ FULL → STARTED → CLOSED
    └───────────────→ CANCELED

CREATED     DB 생성 완료, 공지 메시지 연결 전
RECRUITING  현재 확정자가 정원 미만
FULL        현재 확정자가 정원과 같음
STARTED     시작 시각 도달, 공식 roster snapshot 동결
CLOSED      관리자 종료 또는 운영상 종료 처리
CANCELED    시작 전 취소
상태와 milestone을 분리: “완료 공지를 보냈는가”는 상태가 아니라 recruitment_completed_notified_at 필드입니다. FULL에서 RECRUITING으로 돌아갔다 다시 FULL이 되어도 이 필드가 있으면 완료 공지는 다시 보내지 않습니다.
이벤트시작 전시작 이후
확정자 ✅ 제거철회 처리 후 가장 빠른 대기자 승격. 대기자가 없으면 FULL → RECRUITING공식 roster 변경·승격 없음. 관리자에게 제거 사실만 안내
대기자 ✅ 제거대기열에서 제외무시 또는 감사 로그만
새 ✅ 추가정원 여유 시 확정, 아니면 대기공식 roster에 추가하지 않음

시작 전/후 판정은 actor 처리 지연이 아니라 gateway handler가 기록한 received_at을 기준으로 합니다. received_at < starts_at이면 시작 전 규칙입니다.

5. 세션별 티어 수집 규칙

유효 범위: recruitment_completed_notified_at ≤ tier_activity_at < tier_deadline_at. 하한은 모집 완료 메시지가 Discord에 성공적으로 전송된 시각이며, 상한은 미포함입니다.

어떤 메시지를 인정하는가

  1. 메시지가 설정된 티어 채널에 있어야 합니다.
  2. 작성자 Discord user ID가 해당 세션의 확정자 또는 대기자 roster에 있어야 합니다.
  3. 새 메시지는 created_at, 수정 이벤트는 edited_at을 tier_activity_at으로 사용합니다.
  4. tier_activity_at이 수집 창 안에 있어야 합니다.
  5. 같은 사용자에게 이미 저장된 후보보다 활동 시각이 최신일 때만 upsert합니다.
  6. 활동 시각이 같으면 Discord message ID가 큰 쪽을 선택합니다.

인정 예시

  • 완료 공지 이후 새로 작성한 메시지
  • 과거에 작성한 메시지라도 수집 창 안에서 실제 수정한 경우
  • 수집 창 안에서 여러 번 작성·수정했다면 활동 시각이 가장 최신인 원문
  • 대기자가 수집 창 안에 작성했고 이후 확정자로 승격된 경우

불인정 예시

  • 과거 내전의 기존 메시지를 수정하지 않은 상태로 발견
  • 모집 완료 공지 전 작성·수정
  • 티어 마감 시각과 같거나 이후 작성·수정
  • 해당 세션 roster에 없는 사용자의 메시지
  • 마감 이후 수정으로 바뀐 현재 Discord 원문

저장 방식

tier_submissions UNIQUE(match_id, discord_user_id)

새 qualifying message/edit 도착
  → 기존 row와 (tier_activity_at, message_id) 비교
  → 더 최신이면 raw_tier_message, message_id, activity_at, display_name을 교체
  → 이전 원문 history는 MVP에서 보관하지 않음
  • 현재 저장된 message가 삭제되면 해당 사용자를 미작성으로 되돌립니다.
  • MVP는 과거 후보 history를 저장하지 않으므로 삭제 시 이전 메시지로 자동 fallback하지 않습니다.
  • 마감 이후에는 row를 불변 snapshot으로 취급합니다.
  • 티어 문자열 검증·배틀태그/역할 티어 파싱은 하지 않습니다.
봇 오프라인 중 오래된 메시지 수정: Discord 채널 history는 메시지 생성 순서 중심이므로, 수집 창 전에 작성된 오래된 메시지가 봇 오프라인 중 수정된 사실을 완전하게 복원하기 어렵습니다. MVP는 재시작 시 수집 창 안에 새로 작성된 메시지만 제한적으로 catch-up하고, 오래된 메시지의 오프라인 수정은 사용자 재작성 또는 재수정을 안내합니다.

티어 현황

  • /티어현황: 현재 확정자 중 qualifying submission 보유/미보유 인원 표시
  • /티어현황과 /내전상태 상세에서 작성 완료·미작성 인원을 확인
  • 티어 미작성자 mention, 마감 자동 알림과 전원 완료 알림은 보내지 않으며 마감 이후 작성은 인정하지 않음
  • 수집 창 시작 전에는 “모집 완료 공지 후 수집 시작”으로 응답
  • 현재 확정자 전원이 작성하면 관리자 채널에 매치당 한 번만 안내
  • roster나 티어 메시지가 바뀌면 관리자 현황 화면에서 최신 상태를 다시 계산

6. 반응 이벤트와 참가 순서

arrival_seq의 정확한 정의

세션 actor는 자신의 queue에서 raw reaction event를 하나 꺼낼 때마다 1씩 증가하는 arrival_seq를 부여합니다. 참가자의 reactionOrder는 그 사용자를 활성 상태로 만든 가장 최근 유효 ADD 이벤트의 arrival_seq입니다. 
Discord raw reaction event
  → handler: ✅ / message_id / bot 필터 + received_at 기록 + queue.put_nowait
  → SessionActor: dequeue
  → arrival_seq = next_arrival_seq()
  → ADD/REMOVE/duplicate 상태 전이
  → batch writer
  • 낮은 arrival_seq가 먼저 반응한 참가자입니다.
  • 모든 raw event에 seq가 소비되므로 실제 참가자의 reactionOrder에는 간격이 있을 수 있습니다.
  • 활성 사용자의 중복 ADD는 roster를 바꾸지 않습니다.
  • REMOVE 후 다시 ADD하면 새 ADD의 arrival_seq가 reactionOrder가 되어 대기열 끝으로 갑니다.
  • 표시용 1~10 순위가 필요하면 현재 확정자를 reactionOrder로 정렬한 뒤 파생하며 DB의 원본 값을 다시 번호 매기지 않습니다.

폭주 처리

hot path

  • DB 접근 없음
  • Discord API 호출 없음
  • 티어 채널 검색 없음
  • message_id → actor 메모리 lookup
  • queue 삽입 후 즉시 반환

actor/writer

  • 세션당 consumer 1개로 lock 경쟁 제거
  • set[user_id]로 중복 O(1) 확인
  • 1초 또는 100건 단위 SQLite transaction
  • 정원 도달 milestone과 notification outbox를 같은 transaction에 기록

Discord 연결이 끊긴 동안의 클릭 순서는 복원할 수 없습니다. MVP에서는 별도 DEGRADED_ORDER 상태나 자동 복구 절차를 만들지 않고, mismatch를 발견하면 관리자 채널에 짧게 알리고 수동 판단으로 넘깁니다.

모집 메시지의 봇 seed ✅는 실제 참가자가 0명일 때만 유지합니다. 참가자가 생기면 제거해 표시 숫자를 실제 인원과 맞추고, 마지막 참가자가 반응을 제거하면 비동기 reconciliation 작업이 ✅를 다시 추가합니다.

7. /내전 파싱과 지난 시각 처리

지원 입력

/내전 시간:오후6시20분 모드:6ㄷ6클래식
/내전 시간:오후2시20분
/내전 시간:18:20
/내전 시간:23시 모드:6ㄷ6클래식
  • Unicode NFKC 정규화 후 문자열 앞의 시간 토큰을 파싱하고 나머지를 mode 원문으로 저장합니다.
  • 모드가 없고 관리자 기본 모드도 없으면 mode = null로 정상 생성합니다.
  • 공지 템플릿은 mode가 null이면 해당 줄을 생략합니다. 설정에 따라 표시만 “일반 내전”으로 대체할 수 있습니다.
  • 오전12시 = 00:00, 오후12시 = 12:00, 23시 = 23:00입니다.

지난 시각 기본 흐름

입력현재보다 지난 시각
Reject세션/공지를 생성하지 않음
안내미래 시각으로 다시 입력하도록 안내
past_time_policy: reject
  • 항상 reject하며 자동으로 다음 날을 선택하지 않습니다.
  • match_sessions row를 만들지 않고 “미래 시각으로 다시 입력” 안내만 보냅니다.

/공지문구는 비개발자용 메뉴를 열고 문구 편집과 미리보기 버튼을 함께 제공합니다. 관리자는 시작 제목, 티어 제목, 티어 안내, 작성 양식·예시, 추가 안내만 입력하고 시간·채널·일정은 봇이 자동으로 배치합니다. 모집 완료 공지에는 참가자 목록을 표시하지 않습니다. Jinja 변수와 고급 템플릿 편집 명령은 관리자 화면에 노출하지 않습니다. 저장 결과는 다음 완료 공지부터 재시작 없이 적용하며 Discord 메시지 2,000자 제한을 렌더링 후 검증합니다.

모집 완료 공지는 사용자 mention과 공개 내전 코드를 비활성화합니다. 사용자 호출이 필요한 대기실 안내만 대상 사용자 ID를 allowed_mentions.users에 포함합니다. Jinja sandbox와 StrictUndefined로 객체 내부 접근, 알 수 없는 변수, 2,000자 초과 결과를 저장 단계에서 거부합니다.

mention 안전

  • 모집 공지는 recruitment_role_id 역할 하나만 허용하고 YAML 기반 임의 mention은 차단합니다.
  • 완료 공지는 사용자 mention을 차단하고, 대기실 안내만 해당 미입장자를 허용합니다.
  • 시작 시각 차이가 1시간 미만인 활성 내전이 있으면 나중에 생성한 내전을 대기실 2로 고정 배정합니다.
  • 대기실 안내는 전송 시점의 확정자 중 배정된 음성 채널에 없는 사용자만 허용합니다.
  • @everyone, @here, 역할 mention 권한은 부여하지 않습니다.

9. 주요 데이터 모델과 웹 전달 계약

tier_submissions

  • notification_outbox: kind, match/channel, payload, allowed user IDs, dedupe key, status, attempts, last_error

Balance 웹 전달 DTO

Discord 표시 헤더, 배틀태그 라벨, 역할 줄을 봇에서 재구성하지 않습니다.
{
  "discordUserId": "123456789012345678",
  "discordDisplayName": "lemon",
  "rawTierMessage": "lemon#32146\n마4 / 마4! / 마4",
  "reactionOrder": 17
}
  • reactionOrder는 current roster entry의 actor arrival_seq이며 1부터 연속일 필요가 없습니다.
  • 웹 export 대상은 세션의 현재 확정자입니다. 대기자·철회자는 제외합니다.
  • 티어 미작성 확정자는 payload에서 제외하거나 별도의 missing user ID 목록으로 다루며, 4개 필드에 임의 문자열을 채우지 않습니다.
  • MVP의 NoOpSyncSink는 전송하지 않지만 같은 mapper를 단위 테스트해 향후 API 계약을 고정합니다.

10. 실제 MVP 구현 범위

구현

  • /내전 시간 [모드]와 지난 시각 reject
  • 단일 YAML 설정·모집/모집 완료 텍스트 템플릿
  • 공지 전송과 ✅ 추가
  • raw reaction add/remove, actor arrival_seq, 10명/대기자/승격
  • 완료 공지 한 번과 안전한 allowed_mentions
  • 완료 공지 이후부터 마감 전까지의 최신 티어 원문 upsert
  • /티어현황과 /내전상태 상세의 작성 인원 표시
  • 티어 미작성·전원 완료 후속 mention 없음
  • 전원 작성 관리자 알림 한 번
  • 시작 10분 전 대기실 알림, 시작 전 로스터 변경 계속 반영
  • 시작 시 roster 동결, 시작 후 제거 관리자 알림
  • SQLite repository, 단순 notification outbox, 재시작 복구
  • MatchRepository, SyncSink, NoOpSyncSink
  • 운영 명령 /내전상태, /내전취소, /내전종료

구현하지 않음

  • Redis, 분산 lock, 다중 bot instance, sharding
  • FastAPI server/client 실구현, PostgreSQL schema, 실제 원격 sync
  • 원격 sync outbox와 고급 dead-letter 재처리 UI/운영
  • DEGRADED_ORDER 상태와 정교한 자동 복구 절차
  • 동시 다중 내전과 티어 메시지 세션 선택 UI
  • 티어 문자열 파싱·검증·팀 밸런싱
  • 자동 경고·제재·노쇼 판정
  • 관리자 웹 UI와 관리자별 다중 layout 파일

MVP 완료 기준

  • 18명 burst에서 actor arrival_seq에 따라 확정 10명과 대기자가 결정된다.
  • 과거 티어 메시지는 자동 연결되지 않는다.
  • 완료 공지 후·마감 전 최신 작성/수정 원문만 저장된다.
  • 모드 null과 지난 시각 reject 흐름이 정상 작동한다.
  • 대기실 알림 후에도 시작 전 제거라면 대기자가 승격된다.
  • 시작 이후 reaction은 공식 roster를 바꾸지 않는다.
  • 재시작 후 세션·roster·마감·대기실 알림·cooldown이 복구된다.
  • 웹 mapper가 정확히 4개 필드만 생성한다.

12. Discord Intents와 최소 권한

Intent

  • GUILDS
  • GUILD_MESSAGES
  • GUILD_MESSAGE_REACTIONS
  • MESSAGE_CONTENT — privileged, 티어 원문 수집에 필요

GUILD_MEMBERS와 GUILD_PRESENCES는 MVP에서 사용하지 않습니다.

권한

  • OAuth2 scope: bot, applications.commands
  • 부여: VIEW_CHANNEL, SEND_MESSAGES, READ_MESSAGE_HISTORY, ADD_REACTIONS, EMBED_LINKS
  • 미부여: ADMINISTRATOR, MANAGE_MESSAGES, MENTION_EVERYONE, MANAGE_ROLES, KICK/BAN
  • slash invocation은 일반 사용자 메시지를 만들지 않으며, 취소 시 봇이 작성한 모집 공지만 직접 삭제
  • 대기실 메시지는 명시된 user ID만 allowed_mentions에 포함
공식 근거: Gateway Intents, Reaction Events, Permissions, Allowed Mentions.
