1. 요구사항 충돌 및 불명확한 부분

우선순위쟁점추천 결정설정/영향
P0 6ㄷ6클래식은 12명을 암시하지만 참가 규칙은 10명 고정 모드와 정원을 분리. MVP 기본 정원은 10명, 관리자가 별도 설정할 때만 변경 participant_limit: 10. 모드 문자열에서 정원을 추론하지 않음
P0 시간만 입력했고 이미 지난 경우의 동작 요구대로 정책 분리. 운영 기본값은 next_day, 테스트/보수적 서버는 reject past_time_policy: next_day | reject
P0 모드 생략 시 기본 모드가 정의되지 않음 관리자 프로필의 default_mode 사용. 없으면 공지를 만들지 않고 사용법 오류 반환 관리자별 기본값 필요
P0 티어 마감·대기실 시간이 어떻게 계산되는지 명시 부족 기본값은 시작 30분 전/10분 전. 둘 다 관리자 또는 길드 설정으로 오버라이드 tier_deadline_offset_minutes: 30, lobby_offset_minutes: 10
P0 동시에 여러 내전을 열 때 티어 메시지를 어느 내전에 연결할지 모호 MVP는 길드당 활성 내전 1개만 허용. 다중 내전은 전용 스레드 또는 명시적 매치 선택 기능과 함께 2차로 확장 티어 작성자 연결의 모호성을 제거
P0 완료 후 확정자가 반응을 제거했을 때 재공지 정책 “10명 완료”는 최초 1회만. 대기자 승격 시 승격자 1명과 관리자에게만 별도 안내하고 현재 로스터를 갱신 완료 공지 중복 금지와 승격자 인지를 동시에 만족
P1 언제 로스터 변경을 잠글지 없음 대기실 안내 시각에 로스터를 잠그는 것을 권장. 이후 제거는 상태를 바꾸지 않고 관리자 후보 알림만 생성 roster_lock_offset_minutes: 10
P1 10명 미달 상태에서 대기실 시각 도달 현재 확정자에게는 실제 인원 수를 표시해 입장 안내, 관리자 채널에는 미달 경고. “모집 완료” 문구는 사용하지 않음 참가자 안내를 누락하지 않되 잘못된 완료 표현 방지
P1 관리자 판별 기준과 미등록 관리자 처리 허용 사용자 ID 또는 허용 역할 ID를 길드 설정에 명시. 미등록 사용자의 명령은 거부 Discord의 광범위한 Administrator 권한에 의존하지 않음
P1 티어 메시지 “작성 완료”의 최소 조건 티어를 파싱하지 않으므로 비어 있지 않은 최신 텍스트 메시지만 작성 완료로 간주. 첨부만 있는 메시지는 미작성 기존 Balance 웹의 파싱 책임 유지
P1 Discord 오프라인 동안 추가된 반응의 정확한 순서 현재 반응자 목록은 복구할 수 있어도 정확한 시간 순서는 복구할 수 없음. 순서를 추측하지 말고 DEGRADED_ORDER로 표시해 관리자 결정 요청 공정성 우선. 조용한 재정렬 금지
P2 내전 취소·수동 잠금·상태 조회 명령이 요청에 없음 운영 안전을 위해 .내전취소, .내전상태, .내전마감을 최소 운영 명령으로 MVP에 포함 권장 예약 작업과 잘못 생성된 세션을 안전하게 종료
정확히 한 번 전송의 한계: DB outbox로 중복을 막아도 “Discord 전송 성공 직후, DB 성공 기록 직전”에 프로세스가 종료되면 외부 시스템을 포함한 수학적 exactly-once는 보장할 수 없습니다. 고유 알림 키를 embed footer에 기록하고 재시도 전 최근 봇 메시지를 대조해 effectively-once에 가깝게 만듭니다.

2. 추천 아키텍처

선택 기술

  • Python 3.13+
  • discord.py 2.x
  • asyncio 세션별 Queue/actor
  • aiosqlite + 명시적 SQL migration
  • pydantic-settings로 환경 변수 검증
  • Jinja2 파일 템플릿
  • 표준 zoneinfo.ZoneInfo("Asia/Seoul")
  • pytest, pytest-asyncio

ORM 이식성보다 로컬 SQLite의 단순성과 API 경계를 우선합니다. 향후 Postgres는 FastAPI 서버의 별도 repository로 구현합니다.

레이어와 책임

Discord Adapter명령, raw reaction, tier message, Discord 전송
Application유스케이스, 세션 actor, 스케줄러, outbox worker
DomainMatch, Roster, 정책, 상태 전이, 도메인 이벤트
PortsRepository, NotificationSink, Clock, SyncSink
InfrastructureSQLite, Discord API, 향후 FastAPI client

핵심 컴포넌트

  • MatchCommandService: 관리자 권한, 파싱, 중복 활성 세션 검사, 공지 생성
  • SessionRegistry: announcement_message_id → session actor 메모리 인덱스
  • ReactionIngestor: raw payload 최소 검증 후 큐 삽입
  • MatchSessionActor: 단일 소비자로 순서·중복·승격 결정
  • TierCollector: 티어 채널 메시지/수정/삭제를 참가자 ID와 연결
  • Scheduler: DB의 due job을 실행하고 재시작 시 복구

외부 효과 분리

  • PersistenceBatcher: 이벤트를 1초 또는 100건 단위로 transaction 저장
  • NotificationOutboxWorker: 모집 완료·승격·미작성·대기실 메시지 전송
  • RemoteSyncOutboxWorker: 향후 FastAPI로 재시도 가능한 동기화
  • ReconciliationService: 재시작/불확실 전송/반응 불일치 점검

핵심 상태 흐름

CREATED → RECRUITING → FULL → ROSTER_LOCKED → STARTED → CLOSED
                 ↘              ↘
                  CANCELED       DEGRADED_ORDER (관리자 개입 필요)

참가자 상태: WAITLISTED | CONFIRMED | WITHDRAWN
재반응 규칙: WITHDRAWN 사용자가 다시 ✅ → 기존 순서 복구가 아니라 대기열 맨 뒤에 새 join_seq 부여

모집 생성 시퀀스

  1. 명령 처리기가 관리자·채널·활성 세션을 검증하고 시간을 KST로 파싱합니다.
  2. SQLite에 CREATED 세션을 먼저 저장합니다.
  3. 관리자 템플릿을 렌더링해 공지 채널에 전송하고, 메시지 ID를 저장합니다.
  4. 봇이 ✅ 반응을 추가한 뒤 RECRUITING으로 전환합니다.
  5. 공지 전송 또는 반응 추가 중 실패하면 세션을 CREATE_FAILED로 남겨 재시도/관리자 진단이 가능하게 합니다.

3. MVP 범위

포함 필수 기능

  • .내전 시간 [모드] prefix 명령과 관리자 권한 확인
  • 관리자별 파일 템플릿·규칙·기본 모드
  • 지정 채널 공지와 봇의 ✅ 반응 추가
  • raw add/remove, 순서, 중복 제거, 10명/대기자, 자동 승격
  • 최초 10명 완료 1회 알림 및 제한된 user mention
  • 티어 원문 최신 메시지 수집, 현황, 미작성 알림 5분 cooldown
  • 전원 티어 완료 관리자 알림 1회
  • 대기실 예약 알림 및 재시작 복구
  • SQLite repository, notification outbox, API sync용 port/outbox schema
  • 자동 경고 대신 관리자 후보 알림

제외 2차 이후

  • 자동 경고 부여·누적·제재
  • 티어 문자열 파싱 및 팀 밸런싱
  • FastAPI/PostgreSQL 실서버와 운영 배포
  • 동시 다중 내전, 다중 티어 채널 자동 매칭
  • 고급 관리자 웹 UI·템플릿 편집 UI
  • 노쇼 자동 판정
  • 다중 프로세스/샤드 간 분산 lock
MVP에 추가 권장하는 운영 명령: .내전상태, .내전취소, .내전마감. 예약 작업을 안전하게 정리하려면 취소 명령은 사실상 필수입니다.

완료 기준

  • 18명이 짧은 시간에 반응해도 이벤트 핸들러에서 DB/Discord API 호출이 발생하지 않는다.
  • 동일 사용자 중복 반응은 1명이고, 제거 후 재반응은 대기열 끝으로 간다.
  • 첫 10명 도달 알림은 상태 변동과 재시작을 거쳐도 논리적으로 1회만 생성된다.
  • 확정자 제거 시 가장 이른 대기자가 자동 승격되고 현재 로스터가 일관된다.
  • API가 없거나 장애여도 모집·티어·대기실 흐름이 정상 동작한다.
  • 재시작 후 예정 작업과 cooldown이 SQLite에서 복구된다.
  • 모든 일반 공지는 mention을 막고, 참가자 알림만 명시된 사용자 ID를 허용한다.

5. 주요 데이터 모델

설계 원칙

  • Discord snowflake는 문자열 또는 64-bit integer로 손실 없이 저장합니다.
  • 모든 절대 시각은 UTC로 저장하고, 입력·표시만 Asia/Seoul로 변환합니다.
  • 순서에는 벽시계가 아니라 세션 내부 단조 증가 join_seq를 사용합니다.
  • 표시 이름은 변경될 수 있으므로 snapshot이며 사용자 식별은 항상 Discord user ID입니다.
match_sessions
필드의미
id UUID PK봇이 생성한 전역 매치 ID
guild_id, manager_user_id길드와 실행 관리자
command_channel_id, announcement_channel_id, tier_channel_id, admin_channel_id이름이 아닌 고정 ID

roster_entries + reaction_events

roster_entries는 현재 상태, reaction_events는 감사·복구용 이벤트 로그입니다.

  • roster_entries: (match_id, user_id) UNIQUE, display name snapshot, join_seq, joined/removed/promoted 시각, CONFIRMED | WAITLISTED | WITHDRAWN
  • reaction_events: event UUID, match/user/message/emoji, ADD | REMOVE, gateway 수신 시각, 세션 arrival sequence, 처리 결과, persisted 시각
  • 활성 상태의 중복 ADD와 이미 철회된 사용자의 REMOVE는 이벤트 로그만 남기거나 no-op으로 집계합니다.
tier_messages
  • message_id PK, match_id, user_id, display_name_snapshot
  • raw_content, created_at_utc, edited_at_utc, deleted_at_utc
  • participant_join_seq_snapshot
  • 사용자별 “현재 티어”는 삭제되지 않은 메시지 중 가장 큰 Discord message ID를 선택합니다. 원문을 파싱하지 않습니다.
scheduled_jobs + notification_outbox + sync_outbox
  • scheduled_jobs: kind, due_at, status, attempts, lease_until, dedupe_key UNIQUE
  • notification_outbox: Discord 채널, 메시지 종류, 허용 mention 사용자 목록, payload, marker key, 재시도 상태, sent message ID
  • sync_outbox: aggregate ID/version, immutable JSON payload, idempotency_key UNIQUE, attempt, next_attempt_at, last_error
warning_candidates (MVP에서는 관리자 안내용)

티어 미작성, 잠금 이후 반응 제거, 순서 복구 불가, 노쇼 의심 등의 사실만 기록합니다. warning_issued나 자동 제재 필드는 두지 않습니다.

6. .내전 명령어 파싱 전략

파서 파이프라인

  1. 명령 prefix를 분리하고 Unicode NFKC 정규화, 양끝 공백 제거, 연속 공백 축약
  2. 문자열 앞부분에서만 시간 토큰을 인식하고 나머지 전체를 mode_raw로 보존
  3. 오전/오후를 24시간제로 변환하고 범위를 검증
  4. KST의 오늘 날짜와 결합한 timezone-aware datetime 생성
  5. 이미 지난 시각이면 past_time_policy 적용
  6. 모드가 없으면 관리자 기본 모드 적용
  7. 티어 마감/대기실/잠금 시각을 offset으로 계산하고 최소 준비 시간을 검증

지원 패턴

^(?:(오전|오후)\s*)?(\d{1,2})\s*시(?:\s*(\d{1,2})\s*분)?
|^(\d{1,2}):(\d{2})
  • 오후6시20분 → 18:20
  • 오후2시20분 → 14:20
  • 18:20 → 18:20
  • 23시 → 23:00
  • 오전/오후가 있으면 1~12시, 없으면 0~23시
  • 오전12시 → 00:00, 오후12시 → 12:00

오류와 안전장치

  • 24:00, 18:60, 오후13시 거부
  • 시간 토큰이 문자열 중간에 나타나면 거부
  • min_lead_minutes 기본 15분 권장. 티어 마감이 생성 시각보다 과거가 되는 명령 방지
  • 오류 응답에는 허용 예시와 현재 적용된 과거 시간 정책을 표시
  • 테스트 가능하도록 Clock을 주입하고 시스템 현재 시각 직접 호출 금지

파싱 결과 DTO

ParsedMatchCommand(

8. 반응 이벤트 폭주 처리 방식

핫 패스: 네트워크·DB I/O 없음

on_raw_reaction_add/remove(payload)
  1. guild/message/emoji(✅)/bot 필터
  2. message_id → SessionActor 메모리 조회
  3. 첫 await 전에 process-local arrival_seq 할당
  4. immutable ReactionEvent를 queue.put_nowait()
  5. 즉시 반환

SessionActor (세션당 정확히 1개 consumer)
  1. 현재 active user_id 집합으로 중복 판정
  2. ADD: next_join_seq 부여 → 정원 이하면 CONFIRMED, 이후 WAITLISTED
  3. REMOVE: WITHDRAWN → 확정자였다면 가장 작은 waitlist join_seq 승격
  4. 최초 정원 도달이면 RosterFilled 도메인 이벤트 1개 생성
  5. dirty state / event batch / outbox command를 writer queue로 전달

데이터 구조

  • active_user_ids: set[int] — O(1) 중복 확인
  • confirmed: OrderedDict — 현재 확정자
  • waitlist: deque + tombstone 또는 min-heap — 가장 이른 유효 대기자 승격
  • message_to_session: dict[int, UUID] — 이벤트마다 채널/DB 검색 제거

배치·백프레셔

  • 기본 flush: 1초 또는 100 events, 먼저 충족한 조건
  • SQLite WAL, foreign keys ON, busy timeout 설정
  • 큐 최대치 권장 2,000. 초과는 critical metric + 세션 DEGRADED_ORDER + 관리자 개입
  • 종료 신호에서 새 이벤트 수신 중지 → queue drain → transaction commit
순서의 의미: 저장하는 시각은 Discord 사용자가 클릭한 정확한 서버 시각이 아니라 봇이 gateway event를 받은 시각입니다. 정상 연결 중에는 callback 수신 순서에 따라 arrival_seq를 부여합니다. 오프라인 구간은 정확한 순서를 복구할 수 없습니다.

공지 전송은 outbox에서

참가자 변경과 “완료 알림 생성 필요” 판단은 actor가 하지만 Discord API 호출은 하지 않습니다. SQLite transaction 안에서 로스터 변경과 고유 notification_outbox.dedupe_key = match:{id}:roster-filled 삽입을 함께 수행하고 별도 worker가 전송합니다.

# API 도입 후

# FastAPI 서버 내부
PostgresMatchRepository

ApiMatchRepository를 봇의 유일한 저장소로 즉시 바꾸지 않는 것이 핵심입니다. 원격 장애가 Discord hot path를 멈추지 않게 local repository는 계속 권위 있는 write-ahead store로 둡니다.

동기화 계약 권장안

  • 봇이 match snapshot/version을 만들고 같은 SQLite transaction에서 sync_outbox에 넣습니다.
  • Idempotency-Key: match:{match_uuid}:version:{version}을 사용합니다.
  • FastAPI는 키를 unique constraint로 저장하고 같은 요청은 성공 응답으로 재생합니다.
  • 전송은 exponential backoff + jitter, 최대 시도 후 dead-letter. Discord 처리에는 영향을 주지 않습니다.
  • 서버가 오래된 version을 받으면 무시하고, 새 version만 Postgres transaction으로 반영합니다.

10. 재시작 및 장애 복구 전략

상황복구 동작중복/손실 방지
정상 재시작비종료 세션, 메시지 인덱스, 로스터, due job, cooldown을 SQLite에서 메모리로 복구graceful shutdown에서 queue drain
대기실 시각 전 재시작DB scheduler job을 다시 claimdedupe_key unique

API 장애SQLite commit 성공 유지, sync outbox pending, backoff 재시도Discord event loop와 완전 분리

시작 시 복구 절차

  1. migration 적용과 PRAGMA quick_check 실행
  2. 중단되지 않은 세션과 roster snapshot 로드
  3. announcement_message_id 인덱스와 세션 actor 재생성
  4. outbox의 SENDING 상태 중 lease가 만료된 항목을 PENDING으로 환원
  5. due job을 현재 시각과 비교해 즉시 실행·재예약·MISSED 처리
  6. 선택적 Discord reconciliation은 백그라운드로 수행하고 이벤트 수신을 오래 막지 않음
백업: SQLite 파일을 실행 중 단순 복사하지 말고 SQLite backup API 또는 checkpoint 후 원자적 스냅샷을 사용합니다. 개인정보 보존 기간과 종료 세션 삭제 정책은 운영 전 확정합니다.
